# LogVault Gotchas

- App version MUST come from root `package.json` via `next.config.js`'s `NEXT_PUBLIC_APP_VERSION` — `frontend/package.json`'s own `version` field is a separate file nothing in the release process bumps; it drifted to a stale value for a long time and caused a version-flash-on-load bug that was mistaken for a caching bug for days before the real cause was found.
- Every API/page response MUST set `Cache-Control: no-store` explicitly — a response with only a weak ETag and no explicit directive is legal for a corporate caching proxy to store, causing intermittent stale-content bugs that neither a hard refresh nor Incognito can fix (only the browser's OWN cache is affected by those, not network-infrastructure caches). If you add a new response path, don't forget this.
- Rollup tables (`syslog_*_rollup`) use a recompute-window model (DELETE+INSERT current+previous hour, widened to `ROLLUP_LOOKBACK_HOURS` default 24h) — NEVER convert to increment-on-insert, it looks like an obvious efficiency win but reintroduces double-counting/drift risk on every collector restart or retry.
- Rollup site_id is a SNAPSHOT at build time (resolved once via `known_hosts.ip_address = source_ip`, the RELAY not the actor) — a device's site reassignment only affects new rollup rows going forward, not historical ones. This is intentional, not a bug to "fix" into a live join.
- Any NEW rollup table needs 3 things updated together or widgets silently show empty data: `scripts/schema.sql` (table+indexes), `collector/collector.js` (recompute function, called from `recomputeRollupBucket`), `scripts/backfill-rollups.js` (historical backfill, MUST be run manually once after schema deploy — nothing runs it automatically).
- `getStatsSiteFilter`/`getSiteFilter` (raw-table reads, live join) vs `getRollupSiteFilter` (rollup reads, plain column, site_id pre-resolved) — using the wrong one either breaks RBAC or adds a needless live join. Match the table you're reading.
- `firewall_denies`/`/api/security/firewall-denies` check `action = 'blocked'`, NOT `'deny'` — this deployment's Fortinet parser never emits 'deny'. If you see 'deny' in a diff, that's reintroducing a bug that made this card silently show 0 for a long time.
- `message ILIKE '%...%'` fallbacks sitting next to an already-reliable `structured_data->>'subcategory'` check are a recurring found-and-removed pattern (auth-failures, security summary, health/config-changes) — always verify actual extra recall over 30 days live before adding one back; every instance checked so far caught zero extra rows while costing 10-90x query time.
- `syslog_entries` and `audit_log` are append-only for `logvault_user` (UPDATE/DELETE REVOKEd) — never write app code that UPDATEs/DELETEs them; it will fail at the DB level. `alert_events` is deliberately NOT locked down (API legitimately UPDATEs it for acknowledgement).
- `scripts/schema.sql` and any one-off backfill/migration script that touches `syslog_entries` (e.g. srcip backfill, category backfill) MUST run as `postgres` superuser, not `logvault_user` — the REVOKE above blocks the app role.
- Only 5 EXACT `/api/*` paths are unauthenticated at the proxy: `/api/health`, `/api/stats`, `/api/license-status`, `/api/system/update-available`, `/api/system/last-update-status`. Sub-paths are NOT covered (`/api/stats/summary` still needs a session even though `/api/stats` doesn't) — a prefix-match "fix" here would be a real security regression.
- `installer/Update-LogVault.ps1` (2.25.10+) has DDIVault-style self-healing: before touching anything it snapshots the current git commit + renames `node_modules` (root), `frontend/.next`, and `frontend/node_modules` to `*.lastgood`. Every failure path (git pull, schema-apply, root/frontend npm install, frontend build, service-start, and now-mandatory `/api/health` poll on :3005) calls a shared `Fail-Update` helper instead of a bare `exit 1` — it reverts git to the pre-update commit, restores the 3 snapshots, restarts all 3 services in the documented order (Collector→API→App), re-verifies health, and writes a BOM-free JSON result to `logs/last-update-status.json` (`[System.IO.File]::WriteAllText(..., UTF8Encoding($false))`, NOT `Out-File -Encoding UTF8` — the latter's BOM breaks Node's `JSON.parse` on the reading side). `GET /api/system/last-update-status` (public, both `proxy.ts` and `enforceLicense` exempted) surfaces it to `UpdateFailureBanner.tsx` (admin/super_admin only, via `useSession()` — LogVault has no RBACContext). **Rollback reverts CODE only, not the DB** — a schema-apply failure (real SQL error under `-v ON_ERROR_STOP=1`, not the "psql/POSTGRES_PASSWORD missing" soft-skip case) now also triggers this same rollback rather than just warning, since `schema.sql` isn't applied inside one transaction and a code-level rollback can't undo a partially-applied schema; the old code is still expected to tolerate a few extra/partial columns better than the whole app staying down. `$ErrorActionPreference` is deliberately left at PowerShell's default `'Continue'` in this script (unlike NetVault/DDIVault) — every git/npm/psql call already gates on `$LASTEXITCODE` explicitly, so don't add `= 'Stop'` here, it would introduce a new failure-mode class this script doesn't currently have.
- Port 3005 (Express API) is never firewalled open — the browser never calls it directly, only `proxy.ts` does server-side. Don't add CORS/auth logic assuming a browser could reach it directly.
- `/api/health/device-status`'s `logs_1h` field is deliberately a live query, not the rollup — an hour-bucket SUM has a ±59min edge effect that IS the whole window on a 1h range (verified up to 91% undercount right after each hour boundary). Don't "simplify" it to match the 24h fields' rollup pattern.
- IdleTimeout/Header components must fetch LogVault's OWN `/api/settings` via a relative path, not `getHubUrl() + '/api/settings'` — the hub URL points at NetVault's origin (different port), which the browser correctly CORS-blocks.
- `NEXTAUTH_SECRET` and the `nexvault.session-token` cookie name are shared across the whole NocVault suite — changing the cookie name breaks every app's session simultaneously, never do it in a LogVault-only change.
- Service restarts during a deploy use `sc.exe`, never PowerShell's `Stop-Service` — the latter causes a terminal hang in this environment.
- Backend is plain JavaScript (`api/`, `collector/`) — NEVER use TypeScript syntax in a `.js` file there, even though the frontend is TypeScript.
- `Trend`'s `invert` prop flips which direction (up/down) counts as "good" — used for ingestion-spike-style metrics where a rise is bad, don't assume higher-is-always-green.
- Dropdown/select elements need explicit light+dark background/text color pairs (suite-wide standard) — relying on OS default select styling breaks readability in dark mode.
- When adding a new site-scope RBAC check, audit every sibling route in the same resource group too — site-scoping bugs have historically shipped as "fixed this one route" while an identical sibling route was missed.
- Correlated per-row subqueries against `syslog_entries` (e.g. the old known-bad-hosts query) are an O(N×M) trap that doesn't show up until real data volume — measured up to 130s live before being replaced with a rollup. Be suspicious of any `SELECT (SELECT COUNT(*) FROM syslog_entries WHERE ...)` inside another query's SELECT list.
- A `message ILIKE '%X%'` filter whose match rate approaches 100% of a partition (e.g. severity<=4 matching nearly every row) makes ANY index useless — Postgres correctly chooses a seq scan, and no amount of indexing fixes it; the query needs pre-aggregation (a rollup), not a better index. Check actual selectivity with `EXPLAIN ANALYZE` before assuming an index will help.
- NEVER use `execSync`/`spawnSync`/`readFileSync`-style sync I/O in a request path or any other code the API or collector reaches while serving — it blocks the WHOLE Node event loop until the child exits, so every other in-flight request, every timer, and pg's connection callbacks stall for that entire time. The failure does not look like slowness: pg reports `Connection terminated due to connection timeout` / `timeout exceeded when trying to connect` from a perfectly healthy local database, because its `connectionTimeoutMillis` timer expired while the loop was frozen. DDIVault lost a long time treating that as a pool problem (raising pool `max` and the timeout, neither of which could work) before finding a blocking `execSync` underneath (ddivault 1.28.0). LogVault's `GET /api/stats/disk` had the same bug — a measured ~0.85s full-API freeze per call — fixed in 2.26.6 by switching to the `execFileP` (`promisify(execFile)`) already defined a few lines above it. The remaining `execSync` calls in `api/server.js` are deliberate and safe: `git rev-parse HEAD` is effectively instant, and the `schtasks` ones run as part of the update flow that is about to stop the service anyway.

## Security tab performance + the auth-event data gap (2.30.0)
- **"This endpoint is slow" often means "it queued", not "its query is slow".** The Security tab fired ~15 requests in one burst against `pool max: 10`. Measured live 2026-08-06: `/api/alerts/events/recent-unacked` took **44ms** loading alone and **5,028ms** in that burst — same endpoint, same data, 114x worse purely from waiting on a connection. Individually the security queries are 0.6–1.7s; concurrently they presented as 5–7s. Before optimising any endpoint on a busy tab, time it ALONE first — otherwise you'll rewrite a query that was never the problem. Fixed structurally by making Security's three views sub-tabs (only the active one mounts) plus a 60s response cache.
- **The response cache in `api/server.js` MUST stay keyed on `rbacCacheKey(req.rbac)` and mounted after BOTH `rbacMiddleware` and `enforceLicense`.** Keyed wrong, a site-scoped user gets served an admin-scoped payload (every site's data); mounted before `enforceLicense`, a cached 200 replays for up to 60s past a license expiry that should be returning 402. It only stores 200s, so errors/402/403 are never cached.
- **`gatherSecurityKpis` (api/securityKpis.js) is shared by `/api/security/summary` AND soc.js's `gatherSecurity` — never re-inline it.** These were two hand-written copies of the same six queries and had ALREADY drifted: `/api/security/summary` received the `action='blocked'` correctness fix (the parser never emits `'deny'`) while soc.js's copy did not, so the same "Denied" number read correctly on one tab and 0 on the other.
- **Do NOT strip the `message ILIKE` fallback from `/api/security/after-hours`.** It looks exactly like the redundant fallbacks removed in 2.21.x/2.24.x, but it is the opposite case — measured live 2026-08-06 over 24h: full query **2,870** rows, subcategory-branch-only **0**, ILIKE-branch-only **2,870**. The subcategory branch contributes nothing here and the ILIKE carries 100% of the recall; removing it zeroes the widget. (CLAUDE.md already flagged this one as deliberately unverified — that caution was correct.) It needs an index or rollup, not simplification.
- **Several security panels are structurally empty because the FIREWALL never sends the events, not because of any bug.** Over the full 47-day retention (10.9M rows) `structured_data.subcategory` is NULL on 10,954,302 rows; the only populated value is `login_failed` (748, correctly parsed from `ssl-login-fail` + admin `login`). There has never been a single `login_success` — FortiOS logid `0101039424` does not appear at all. So `brute_force_success`, whose self-join requires `subcategory='login_success'`, can only ever return 0 while costing ~1.3s. The `subtype='vpn'` rows that DO arrive (6,442/24h) are `ssl-alert` / `ssl-exit-error` / IPsec `negotiate` — transport noise, not auth outcomes — so the parser is right to leave subcategory unset. Fix is on the FortiGate (enable authentication event logging), not in LogVault. Note this also supersedes the older "this FortiGate doesn't send UTM" belief: UTM now arrives at ~126k rows/24h.
- **`received_at > NOW() - make_interval(hours => $1)` costs ~600ms of PLANNING TIME per query on `syslog_entries` — pass an explicit cutoff timestamp instead.** `syslog_entries` is the ONLY partitioned table here (56 daily partitions; `alert_events`, `entity_risk`, `known_hosts` and every rollup table are plain). `NOW()` is STABLE, not IMMUTABLE, so the cutoff is not a plan-time constant and the planner must consider all 56 partitions and their indexes on EVERY call before pruning at execution. Measured live 2026-08-06 on the auth-failures query: `NOW() - make_interval` = **planning 566ms + execution 6ms**; `received_at > $1` with a JS-computed `new Date(Date.now() - hours*3600*1000)` = **planning 2.5ms + execution 6ms**. Same 19 partitions scanned, identical results, ~30x faster end to end. Verified equivalent on 6 query shapes (4,376ms -> 132ms, all counts byte-identical) before shipping. **Only worth doing for `syslog_entries`** — the same pattern on `alert_events` plans in 0.143ms, so converting non-partitioned queries is pointless churn. Converted in 2.30.1: `api/securityKpis.js` (all 8), `/api/health/summary` (5), and the single-line security endpoints. **~70 occurrences remain across `api/server.js`, `api/soc.js` and `api/reports.js`** — convert them the same way, but check each first: some use `$1` twice for a current-vs-previous comparison window (e.g. soc.js `gatherTopCountries`' `$1 * 2`), which needs two timestamps rather than a mechanical swap.
- **EXPLAIN ANALYZE's "Execution Time" will hide this completely.** The queries above report 6-10ms execution while the real client round-trip is 600-750ms. If a query is measurably slow from the app but EXPLAIN says it's fast, read the **Planning Time** line before assuming a cold cache or a bad index — on a heavily partitioned table planning is routinely 50-100x the execution cost.
- **`SecurityAnalysis.tsx` loads per-section, not all-at-once — keep it that way when adding a panel.** It used to run one `fetchAll()` firing all 13 endpoints on mount regardless of the active section, so opening Detections paid for all nine sections to render Overview's three panels. That is precisely why Overview felt slow while every other section felt instant: their data had already been fetched behind it. Now `fetchCore()` (summary + wireless-auth, always) plus `fetchSection(activeSection)`. Overview: 13 requests -> 4. **If you add a panel, add its endpoint to that section's case in `fetchSection` — the map was verified against the JSX, and a missing entry renders an empty panel with no error.** Two subtleties: `summary` must stay in core because it drives the eight KPI cards AND five tab-bar alert dots; and the VPN dot now reads `summary.vpn_login_failures` rather than scanning the full `vpn-events` payload, which existed solely to colour one dot on every section.
- **`TimeRangePicker`'s auto-refresh interval holds `onRefreshNow` in a ref — do not "simplify" it back to a direct call.** The effect depends only on `[refreshInterval]` on purpose: adding `onRefreshNow` to the deps would restart the countdown every time a parent re-created its callback. That means the `setInterval` closes over whatever callback existed when it was created, for its whole life. Harmless while every caller passed a fetch-everything function whose identity only changed with `hours` — and a real bug the moment `SecurityAnalysis` made refresh section-aware in 2.31.1, because the stale closure then refreshed whichever section was open when the timer started (sitting on IPS/Threats silently re-fetched Overview every 30s). Fixed in 2.31.2 with a ref holding the live callback, invoked via `queueMicrotask` so the fetch stays out of the `setCountdown` updater (updaters must be pure; React may run them more than once). Shared by NetworkHealth, ReportsTab, SocOverview and SecurityAnalysis, so any caller passing an identity-changing callback depends on this.
