# LogVault Gotchas

- App version MUST come from root `package.json` via `next.config.js`'s `NEXT_PUBLIC_APP_VERSION` — `frontend/package.json`'s own `version` field is a separate file nothing in the release process bumps; it drifted to a stale value for a long time and caused a version-flash-on-load bug that was mistaken for a caching bug for days before the real cause was found.
- Every API/page response MUST set `Cache-Control: no-store` explicitly — a response with only a weak ETag and no explicit directive is legal for a corporate caching proxy to store, causing intermittent stale-content bugs that neither a hard refresh nor Incognito can fix (only the browser's OWN cache is affected by those, not network-infrastructure caches). If you add a new response path, don't forget this.
- Rollup tables (`syslog_*_rollup`) use a recompute-window model (DELETE+INSERT current+previous hour, widened to `ROLLUP_LOOKBACK_HOURS` default 24h) — NEVER convert to increment-on-insert, it looks like an obvious efficiency win but reintroduces double-counting/drift risk on every collector restart or retry.
- Rollup site_id is a SNAPSHOT at build time (resolved once via `known_hosts.ip_address = source_ip`, the RELAY not the actor) — a device's site reassignment only affects new rollup rows going forward, not historical ones. This is intentional, not a bug to "fix" into a live join.
- Any NEW rollup table needs 3 things updated together or widgets silently show empty data: `scripts/schema.sql` (table+indexes), `collector/collector.js` (recompute function, called from `recomputeRollupBucket`), `scripts/backfill-rollups.js` (historical backfill, MUST be run manually once after schema deploy — nothing runs it automatically).
- `getStatsSiteFilter`/`getSiteFilter` (raw-table reads, live join) vs `getRollupSiteFilter` (rollup reads, plain column, site_id pre-resolved) — using the wrong one either breaks RBAC or adds a needless live join. Match the table you're reading.
- `firewall_denies`/`/api/security/firewall-denies` check `action = 'blocked'`, NOT `'deny'` — this deployment's Fortinet parser never emits 'deny'. If you see 'deny' in a diff, that's reintroducing a bug that made this card silently show 0 for a long time.
- `message ILIKE '%...%'` fallbacks sitting next to an already-reliable `structured_data->>'subcategory'` check are a recurring found-and-removed pattern (auth-failures, security summary, health/config-changes) — always verify actual extra recall over 30 days live before adding one back; every instance checked so far caught zero extra rows while costing 10-90x query time.
- `syslog_entries` and `audit_log` are append-only for `logvault_user` (UPDATE/DELETE REVOKEd) — never write app code that UPDATEs/DELETEs them; it will fail at the DB level. `alert_events` is deliberately NOT locked down (API legitimately UPDATEs it for acknowledgement).
- `scripts/schema.sql` and any one-off backfill/migration script that touches `syslog_entries` (e.g. srcip backfill, category backfill) MUST run as `postgres` superuser, not `logvault_user` — the REVOKE above blocks the app role.
- Only 5 EXACT `/api/*` paths are unauthenticated at the proxy: `/api/health`, `/api/stats`, `/api/license-status`, `/api/system/update-available`, `/api/system/last-update-status`. Sub-paths are NOT covered (`/api/stats/summary` still needs a session even though `/api/stats` doesn't) — a prefix-match "fix" here would be a real security regression.
- `installer/Update-LogVault.ps1` (2.25.10+) has DDIVault-style self-healing: before touching anything it snapshots the current git commit + renames `node_modules` (root), `frontend/.next`, and `frontend/node_modules` to `*.lastgood`. Every failure path (git pull, schema-apply, root/frontend npm install, frontend build, service-start, and now-mandatory `/api/health` poll on :3005) calls a shared `Fail-Update` helper instead of a bare `exit 1` — it reverts git to the pre-update commit, restores the 3 snapshots, restarts all 3 services in the documented order (Collector→API→App), re-verifies health, and writes a BOM-free JSON result to `logs/last-update-status.json` (`[System.IO.File]::WriteAllText(..., UTF8Encoding($false))`, NOT `Out-File -Encoding UTF8` — the latter's BOM breaks Node's `JSON.parse` on the reading side). `GET /api/system/last-update-status` (public, both `proxy.ts` and `enforceLicense` exempted) surfaces it to `UpdateFailureBanner.tsx` (admin/super_admin only, via `useSession()` — LogVault has no RBACContext). **Rollback reverts CODE only, not the DB** — a schema-apply failure (real SQL error under `-v ON_ERROR_STOP=1`, not the "psql/POSTGRES_PASSWORD missing" soft-skip case) now also triggers this same rollback rather than just warning, since `schema.sql` isn't applied inside one transaction and a code-level rollback can't undo a partially-applied schema; the old code is still expected to tolerate a few extra/partial columns better than the whole app staying down. `$ErrorActionPreference` is deliberately left at PowerShell's default `'Continue'` in this script (unlike NetVault/DDIVault) — every git/npm/psql call already gates on `$LASTEXITCODE` explicitly, so don't add `= 'Stop'` here, it would introduce a new failure-mode class this script doesn't currently have.
- Port 3005 (Express API) is never firewalled open — the browser never calls it directly, only `proxy.ts` does server-side. Don't add CORS/auth logic assuming a browser could reach it directly.
- `/api/health/device-status`'s `logs_1h` field is deliberately a live query, not the rollup — an hour-bucket SUM has a ±59min edge effect that IS the whole window on a 1h range (verified up to 91% undercount right after each hour boundary). Don't "simplify" it to match the 24h fields' rollup pattern.
- IdleTimeout/Header components must fetch LogVault's OWN `/api/settings` via a relative path, not `getHubUrl() + '/api/settings'` — the hub URL points at NetVault's origin (different port), which the browser correctly CORS-blocks.
- `NEXTAUTH_SECRET` and the `nexvault.session-token` cookie name are shared across the whole NocVault suite — changing the cookie name breaks every app's session simultaneously, never do it in a LogVault-only change.
- Service restarts during a deploy use `sc.exe`, never PowerShell's `Stop-Service` — the latter causes a terminal hang in this environment.
- Backend is plain JavaScript (`api/`, `collector/`) — NEVER use TypeScript syntax in a `.js` file there, even though the frontend is TypeScript.
- `Trend`'s `invert` prop flips which direction (up/down) counts as "good" — used for ingestion-spike-style metrics where a rise is bad, don't assume higher-is-always-green.
- Dropdown/select elements need explicit light+dark background/text color pairs (suite-wide standard) — relying on OS default select styling breaks readability in dark mode.
- When adding a new site-scope RBAC check, audit every sibling route in the same resource group too — site-scoping bugs have historically shipped as "fixed this one route" while an identical sibling route was missed.
- Correlated per-row subqueries against `syslog_entries` (e.g. the old known-bad-hosts query) are an O(N×M) trap that doesn't show up until real data volume — measured up to 130s live before being replaced with a rollup. Be suspicious of any `SELECT (SELECT COUNT(*) FROM syslog_entries WHERE ...)` inside another query's SELECT list.
- A `message ILIKE '%X%'` filter whose match rate approaches 100% of a partition (e.g. severity<=4 matching nearly every row) makes ANY index useless — Postgres correctly chooses a seq scan, and no amount of indexing fixes it; the query needs pre-aggregation (a rollup), not a better index. Check actual selectivity with `EXPLAIN ANALYZE` before assuming an index will help.
